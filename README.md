# Claude Code Harness

Claude Code 기반 개발 작업을 더 일관되고 안전하게 진행하기 위한 작업 규칙 저장소입니다.

이 저장소의 목적은 Claude Code에게 매번 긴 설명을 반복하지 않고, 필요한 작업 규칙만 읽어 분석 → 계획 → 승인 → 구현 → 검증 순서로 작업하도록 하는 것입니다.

---

## 목적

이 저장소는 다음 문제를 줄이기 위해 사용합니다.

1. Claude Code가 바로 구현부터 시작하는 문제
2. 한 번에 너무 많은 파일을 수정하는 문제
3. PR 범위가 커지고 목적이 섞이는 문제
4. DB 변경이나 migration을 충분한 검토 없이 진행하는 문제
5. 매번 긴 프롬프트를 작성해야 하는 비효율
6. 구현 후 검증 없이 완료로 판단하는 문제

---

## 핵심 원칙

```text
분석 없이 구현하지 않는다.
승인 없이 파일을 수정하지 않는다.
작업 범위를 작게 나눈다.
검증 없이 완료라고 말하지 않는다.
필요한 harness 문서만 읽는다.
```

## 저장소 구조

```text
harness-dev/
├─ README.md
└─ harness/
   ├─ common.md
   ├─ git.md
   ├─ db.md
   └─ ui-ux.md
```

## 각 문서의 역할

### `harness/common.md`

모든 작업에 공통으로 적용되는 기본 작업 규칙입니다.

주요 내용:

```text
- 요구사항 확인
- 현재 상태 분석
- 변경 영향 범위 정리
- 작업 계획 작성
- 사용자 승인 대기
- 구현
- 검증
- 결과 보고
```

기본적으로 모든 작업에서 적용합니다.

---

### `harness/git.md`

Git 및 PR 단위 작업을 위한 형상관리 규칙입니다.

주요 내용:

```text
- 하나의 PR에는 하나의 명확한 목적만 포함
- 관련 없는 기능 구현, 리팩토링, 문서 정리를 섞지 않음
- 기능 완성에 직접 필요한 schema/migration, 구현 코드, 테스트는 같은 PR에 포함 가능
- 사용자 승인 없이 git add, commit, push 금지
- 변경 파일과 검증 방법 보고
```

작업 범위가 과도하게 확장되지 않도록 통제하는 역할을 합니다.

---

### `harness/db.md`

DB 구조, migration, schema 변경을 다룰 때 사용하는 규칙입니다.

주요 내용:

```text
- migration 작성 전 현재 DB 구조 분석
- 기존 데이터 영향 범위 확인
- nullable/default/FK/index/unique 검토
- rollback 또는 복구 가능성 검토
- 사용자 승인 전 migration 파일 생성 금지
- 운영 DB 직접 변경 금지
```

DB 변경이 포함된 작업에서만 읽고 적용합니다.

---

### `harness/ui-ux.md`

UI 또는 UX 변경을 다룰 때 사용하는 규칙입니다.

주요 내용:

```text
- 화면 목적과 사용자 시나리오 먼저 확인
- 모바일/데스크톱 우선순위 판단
- 정보 우선순위와 CTA 정의
- 기존 디자인 시스템 우선
- 빈 상태, 오류 상태, 접근성 검토
- 구현 전 UI 설계와 영향 범위 정리
```

UI/UX 변경이 포함된 작업에서만 읽고 적용합니다.

---

## Harness 선택 규칙

모든 작업에서 모든 문서를 읽지 않습니다.

작업에 필요한 문서만 선택합니다.

```text
일반 코드 작업
→ common.md + git.md

DB/model/migration 변경
→ common.md + git.md + db.md

UI/UX 변경
→ common.md + git.md + ui-ux.md

DB와 UI를 모두 변경
→ common.md + git.md + db.md + ui-ux.md
```

프로젝트별 `CLAUDE.md`가 있다면 해당 문서를 먼저 확인하고, 프로젝트에서 지정한 harness만 추가로 읽습니다.

## 권장 작업 흐름

```text
1. 관련 harness 문서 확인
2. 요구사항 확인
3. 현재 코드 구조 분석
4. 변경 영향 범위 정리
5. PR 단위 작업 계획 작성
6. 사용자 승인 대기
7. 구현
8. 검증
9. 결과 보고
```

---

## 승인 전 금지 작업

사용자 승인 없이 아래 작업을 수행하지 않습니다.

```text
- 파일 생성
- 파일 수정
- 파일 삭제
- 패키지 설치
- DB migration 작성
- DB migration 실행
- 환경변수 변경
- git add
- git commit
- git push
- 배포 명령 실행
- 기존 기능 제거
```

---

## 승인 문구

아래와 같은 명시적 승인 문구가 있을 때 실제 구현을 진행합니다.

```text
진행
구현 진행
PR 진행
수정 진행
적용해
DB 변경 진행
migration 작성 진행
```

단, 승인은 현재 합의된 작업 범위에만 적용합니다.

작업 중 새로운 변경이 필요해져 승인 범위를 벗어나는 경우 다시 보고하고 확인을 받습니다.

## Claude Code에 전달할 기본 프롬프트

### 일반 작업

```text
이 프로젝트는 harness-dev 기준으로 진행합니다.

먼저 다음 문서를 읽고 적용하세요.

- harness/common.md
- harness/git.md

아직 구현하지 마세요.
현재 코드 구조와 영향 범위를 분석하고 PR 단위 작업 계획만 작성하세요.
```

### DB 변경이 포함된 작업

```text
이 작업은 DB 변경이 포함됩니다.

다음 문서를 기준으로 진행하세요.

- harness/common.md
- harness/git.md
- harness/db.md

아직 migration을 작성하지 마세요.
현재 DB 구조와 관련 코드, 기존 데이터 영향 범위, 변경 계획을 먼저 정리하세요.
```

### UI/UX 변경이 포함된 작업

```text
이 작업은 UI/UX 변경이 포함됩니다.

다음 문서를 기준으로 진행하세요.

- harness/common.md
- harness/git.md
- harness/ui-ux.md

아직 UI 파일을 수정하지 마세요.
현재 화면 구조와 사용자 흐름, 변경 영향 범위, 구현 계획을 먼저 정리하세요.
```

## 현재 범위

현재 포함된 항목:

```text
- 공통 작업 규칙
- Git / PR 형상관리 규칙
- DB / Migration 규칙
- UI / UX 규칙
```

현재 포함하지 않은 항목:

```text
- 테스트/QA 전용 하네스
- 보안 전용 하네스
- 문서화 전용 하네스
- Claude Code hooks
- slash command
```

새 하네스는 미리 많이 만들지 않고, 실제 프로젝트에서 반복되는 요구가 확인될 때 점진적으로 추가합니다.

---

## 운영 원칙

```text
1. 반복되는 Claude Code 지시를 줄인다.
2. 작업 시작 전 분석과 계획을 강제한다.
3. PR 단위로 작은 작업을 유지한다.
4. DB 변경 리스크를 낮춘다.
5. UI 변경을 구현 전에 검토한다.
6. 검증 가능한 결과 보고를 만든다.
7. 작업과 관계없는 harness 문서는 읽지 않는다.
```

규칙이 과도하게 길어지면 오히려 작업 효율과 토큰 사용량이 악화될 수 있으므로, 문서는 짧고 실행 가능한 형태를 우선합니다.

---

## 프로젝트 적용 방식

프로젝트 루트의 `CLAUDE.md`에서 이 저장소의 harness 문서를 선택적으로 참조하는 방식을 권장합니다.

예시:

```text
이 프로젝트는 harness-dev 기준으로 진행합니다.

기본:
- harness/common.md
- harness/git.md

DB 변경 시 추가:
- harness/db.md

UI/UX 변경 시 추가:
- harness/ui-ux.md

관련 문서만 읽고 적용합니다.
현재 작업과 관계없는 harness 문서는 읽지 않습니다.

구현 전 현재 코드와 영향 범위를 분석하고 계획을 제시합니다.
사용자가 "진행"이라고 승인하기 전까지 파일을 수정하지 않습니다.
```

## 한 줄 요약
