# Common Harness

## 목적

모든 Claude Code 작업에 공통으로 적용되는 최소 작업 규칙을 정의한다.

목표:

1. 구현 전에 현재 상태와 영향 범위를 확인한다.
2. 작업을 작고 검증 가능한 범위로 유지한다.
3. 합의된 범위를 벗어나 임의로 수정하지 않는다.
4. 구현 후 검증 결과와 남은 리스크를 명확히 보고한다.
5. 불확실한 요구사항은 추측하지 않는다.

---

## 핵심 원칙

```text
분석 없이 구현하지 않는다.
승인 범위를 넘어 수정하지 않는다.
관련 없는 변경을 섞지 않는다.
검증 없이 완료라고 말하지 않는다.
필요한 규칙만 읽고 반복 설명하지 않는다.
```

---

## 기본 작업 흐름

```text
1. 요구사항 확인
2. 현재 코드/상태 확인
3. 영향 범위와 불확실성 정리
4. 작업 계획 제시
5. 사용자 승인
6. 승인된 범위만 구현
7. 검증
8. 결과 보고
```

단순하고 범위가 명확한 작업은 분석과 계획을 간결하게 합칠 수 있다.

---

## 작업 전 규칙

1. 관련 코드와 프로젝트 문서를 먼저 확인한다.
2. 새 구조를 만들기 전에 기존 구현을 재사용할 수 있는지 확인한다.
3. 변경 예정 파일과 변경 이유를 제시한다.
4. 요구사항과 관계없는 리팩토링, 정리, 기능 추가는 포함하지 않는다.
5. 기존 동작을 변경하거나 제거해야 하면 구현 전에 영향 범위를 알린다.
6. 불확실성이 결과에 영향을 주면 질문하고, 영향이 없다면 불필요한 질문을 만들지 않는다.
7. 작업 유형별 harness가 있으면 현재 작업과 관련된 문서만 추가로 읽는다.
8. 읽은 harness 내용을 매번 길게 요약하지 않는다. 사용자가 요청하거나 충돌 확인이 필요할 때만 요약한다.

---

## 승인 규칙

파일 생성·수정·삭제 등 실제 변경은 사용자의 명시적 승인 범위 안에서만 수행한다.

승인으로 볼 수 있는 표현 예:

```text
진행
구현 진행
PR 진행
수정 진행
적용해
```

사용자가 특정 파일이나 변경 내용을 명확히 지정하여 직접 수정을 요청한 경우에는 그 요청 자체를 해당 범위의 승인으로 본다.

단:

- 이전 계획보다 범위가 커지는 경우
- 새로운 파일/패키지/DB 변경 등 추가 영향이 생기는 경우
- 승인된 목적과 다른 변경이 필요한 경우

작업을 멈추고 추가 범위를 먼저 보고한다.

---

## 승인 전 금지 작업

승인 없이 다음 작업을 수행하지 않는다.

```text
- 파일 생성/수정/삭제
- 패키지 설치
- DB migration 생성 또는 실행
- 환경변수 변경
- git add / commit / push
- merge / rebase / reset
- 배포 명령 실행
- 기존 기능 제거
- 인증/권한 구조 변경
```

작업 유형별 harness에 더 엄격한 제한이 있으면 해당 규칙을 따른다.

---

## 범위 관리

- 하나의 작업에는 하나의 명확한 목적을 둔다.
- 구현 중 별도 문제를 발견해도 현재 목적에 필요하지 않으면 수정하지 않는다.
- MVP 밖의 아이디어는 필요할 때만 제안하고 자동으로 구현하지 않는다.
- 변경 파일 수나 영향 범위가 예상보다 커지면 작업을 계속하기 전에 보고한다.
- 기존 코드 스타일, 폴더 구조, 네이밍을 우선한다.

---

## 구현 전 출력

구현 전에는 필요한 정보만 간결하게 제시한다.

```text
## 현재 상태
- 확인한 코드/동작
- 재사용 가능한 부분

## 변경 계획
- 목표
- 변경 예정 파일과 이유
- 검증 방법

## 확인 필요
- 구현을 막는 불확실성 또는 추가 승인 사항
```

해당 항목이 없으면 빈 섹션을 억지로 출력하지 않는다.

---

## 구현 규칙

1. 승인된 범위만 수정한다.
2. 기존 기능과 패턴을 가능한 재사용한다.
3. 같은 목적을 위해 불필요한 추상화나 미래 기능을 미리 만들지 않는다.
4. 관련 없는 파일 포맷팅이나 코드 정리를 섞지 않는다.
5. 구현 중 설계 전제가 틀렸음을 발견하면 임의로 우회하지 않고 보고한다.
6. DB, Git, UI/UX 등 별도 harness가 적용되는 변경은 해당 규칙도 함께 따른다.

---

## 검증

구현 후 변경 범위에 맞는 검증을 수행한다.

최소한 다음을 구분해서 보고한다.

```text
- 실행한 검증
- 검증 결과
- 실행하지 못한 검증과 이유
- 남은 리스크
```

검증하지 않은 동작을 정상이라고 단정하지 않는다.

---

## 구현 후 보고

```text
## 작업 결과

### 변경 파일
- 파일: 변경 이유

### 검증
- 실행:
- 결과:

### 미검증 / 남은 리스크
-
```

필요한 경우에만 다음 단계나 PR 설명을 추가한다.

---

## 규칙 우선순위

규칙이 충돌하면 아래 순서로 적용한다.

```text
1. 사용자의 현재 명시 요청
2. 프로젝트 CLAUDE.md
3. 현재 작업에 해당하는 작업 유형별 harness
4. common harness
5. 기존 프로젝트 코드/문서의 관례
```

작업 유형별 harness는 common을 대체하는 문서가 아니라,
특정 작업에 더 구체적인 규칙을 추가하는 문서다.

---

## 토큰 / 문맥 관리

- 현재 작업과 관련된 문서만 읽는다.
- 이미 확인한 내용을 불필요하게 반복하지 않는다.
- 분석 결과는 구현 판단에 필요한 내용 위주로 요약한다.
- 긴 체크리스트를 기계적으로 출력하지 않는다.
- 코드에서 확인 가능한 내용을 사용자에게 다시 질문하지 않는다.
- 설계 단계에서 구현 세부사항을 과도하게 확정하지 않는다.

---

## 한 줄 원칙

```text
먼저 확인하고, 범위를 합의하고, 승인된 만큼만 구현하고, 검증해서 보고한다.
```
