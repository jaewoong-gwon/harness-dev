# Common Harness

## 목적

이 문서는 Claude Code 기반 작업에서 모든 작업 유형에 공통으로 적용되는 기본 규칙을 정의한다.

목표는 다음과 같다.

1. 바로 구현하지 않고 먼저 분석한다.
2. 작업 범위를 작고 검증 가능한 단위로 나눈다.
3. 사용자의 승인 전에는 파일을 수정하지 않는다.
4. 구현 후 검증 결과와 남은 리스크를 보고한다.
5. 요구사항이 모호한 경우 추측하지 않고 질문한다.

---

## 기본 작업 흐름

Claude는 모든 작업을 아래 순서로 진행한다.

```text
1. 요구사항 확인
2. 현재 상태 분석
3. 변경 영향 범위 정리
4. 작업 계획 작성
5. 사용자 승인 대기
6. 구현
7. 검증
8. 결과 보고
```

---

## 공통 규칙

1. 사용자가 명시적으로 구현을 요청하기 전까지 파일을 생성, 수정, 삭제하지 않는다.
2. 사용자가 “진행”, “구현 진행”, “PR 진행” 등으로 승인하기 전까지 실제 작업을 하지 않는다.
3. 작업 전에는 반드시 현재 코드 구조와 관련 파일을 먼저 확인한다.
4. 변경 전에는 변경 예정 파일 목록과 각 파일을 변경하는 이유를 설명한다.
5. 한 번에 여러 목적의 작업을 섞지 않는다.
6. 요구사항이 모호하면 임의로 추측하지 않고 질문한다.
7. MVP 범위를 벗어나는 기능은 제안만 하고 구현하지 않는다.
8. 기존 코드 스타일, 폴더 구조, 네이밍 규칙을 우선 존중한다.
9. 기존 기능을 제거하거나 동작을 바꾸는 경우 반드시 사전에 영향 범위를 보고한다.
10. 구현 후에는 실행한 검증과 실행하지 못한 검증을 구분해서 보고한다.

---

## 금지 사항

사용자 승인 없이 다음 작업을 수행하지 않는다.

```text
- 파일 대량 수정
- 파일 삭제
- 폴더 구조 대규모 변경
- 패키지 설치
- DB migration 작성 또는 실행
- 환경변수 변경
- git add
- git commit
- git push
- 배포 명령 실행
- 기존 기능 제거
- 인증/권한 로직 변경
```

## 분석 단계 출력 형식

구현 전 분석 단계에서는 아래 형식으로 답변한다.

```text
## 현재 상태 분석

### 확인한 내용
- 

### 관련 파일
- 

### 변경이 필요한 이유
- 

### 변경 영향 범위
- 

### 불확실한 부분
- 

### 사용자 확인 필요 사항
- 
```

---

## 계획 단계 출력 형식

작업 계획은 아래 형식으로 작성한다.

```text
## 작업 계획

### 목표
- 

### 작업 범위
- 

### 제외할 작업
- 

### 변경 예정 파일
- 파일명:
  - 변경 이유:

### 검증 방법
- 

### 남은 리스크
- 
```

---

## 구현 후 보고 형식

구현 후에는 아래 형식으로 보고한다.

```text
## 작업 결과

### 변경한 파일
- 

### 변경 내용
- 

### 검증 결과
- 실행한 검증:
- 결과:

### 실행하지 못한 검증
- 항목:
- 이유:

### 남은 리스크
- 

### 다음 단계 제안
- 
```

---

## 승인 문구 기준

아래 표현이 있기 전까지 실제 파일 수정은 하지 않는다.

```text
진행
구현 진행
PR 진행
수정 진행
적용해
```

단, 사용자가 명확히 코드 수정 또는 파일 생성을 요청한 경우에는 해당 작업 범위 안에서만 진행한다.

---

## 우선순위

규칙이 충돌할 경우 아래 우선순위를 따른다.

```text
1. 사용자 명시 요청
2. 프로젝트 CLAUDE.md
3. 이 common harness
4. 작업 유형별 harness
5. 기존 코드 스타일
```

---

## 핵심 원칙

```text
분석 없이 구현하지 않는다.
승인 없이 수정하지 않는다.
검증 없이 완료라고 말하지 않는다.
```
