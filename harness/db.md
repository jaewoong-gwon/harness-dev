# DB / Migration Harness

## 목적

DB schema, migration, 데이터 변경 작업에서 기존 데이터와 서비스 동작을 보호하기 위한 공통 규칙을 정의한다.

목표:

1. DB 변경 전에 현재 구조와 사용 위치를 확인한다.
2. 기존 데이터 영향과 복구 가능성을 먼저 검토한다.
3. schema 변경과 data migration을 구분한다.
4. 승인 없이 migration을 생성하거나 실행하지 않는다.
5. 구현 후 실제 migration과 관련 기능을 검증한다.

---

## 핵심 원칙

```text
DB는 먼저 분석한다.
변경 이유와 영향 범위를 설명한다.
destructive change는 더 엄격하게 다룬다.
migration 생성과 실행을 구분한다.
기능에 필요한 DB 변경은 같은 PR에 포함할 수 있다.
검증 없이 안전하다고 단정하지 않는다.
```

---

## 적용 범위

다음 작업에 이 harness를 적용한다.

```text
- 새 테이블/모델 추가
- 컬럼/필드 추가·수정·삭제
- index / unique / foreign key / constraint 변경
- migration 생성 또는 실행
- schema migration
- data migration / backfill
- 기존 데이터 일괄 수정
- DB 권한/정책 변경
```

단순 조회 로직 변경만 있고 schema나 데이터 변경이 없다면 필요한 부분만 적용한다.

---

## 작업 전 확인

DB 변경 전에 현재 프로젝트에서 관련된 부분만 확인한다.

```text
- 현재 schema/model 정의
- 기존 migration 이력
- 해당 데이터의 생성/조회/수정 위치
- 기존 데이터 존재 여부와 형태
- 관계 및 삭제 정책
- 현재 DB 엔진과 프로젝트 제약
- 관련 테스트
```

API, UI, 타입, 권한 정책 등은 실제로 영향받는 프로젝트에서만 추가로 확인한다.

---

## 변경 설계 시 확인할 사항

새 테이블/필드 또는 schema 변경을 제안할 때 필요한 항목을 검토한다.

```text
- 새 구조가 실제로 필요한가?
- 기존 구조 확장으로 해결 가능한가?
- null 허용 여부
- default 필요 여부
- unique / constraint 필요 여부
- index 필요 여부
- foreign key 및 삭제 정책
- 기존 데이터 backfill 필요 여부
- 과거 기록 보존 방식
- 기존 코드와의 호환성
- rollback 또는 복구 가능성
```

모든 항목을 기계적으로 채우지 말고, 현재 변경에 해당하는 것만 설명한다.

---

## Migration 원칙

1. migration은 schema 변경의 결과물이지 설계 시작점이 아니다.
2. migration 생성 전에 model/schema 변경안과 영향 범위를 먼저 확인한다.
3. migration 파일 생성과 migration 실행은 별도 작업으로 취급한다.
4. 운영 환경 migration 실행은 별도 승인 없이는 수행하지 않는다.
5. 자동 생성된 migration도 내용을 검토한 뒤 사용한다.
6. 기존 migration 파일을 임의로 다시 쓰지 않는다. 필요한 경우 새 migration으로 보정하는 것을 우선한다.
7. 기능 구현에 직접 필요한 model + migration + 테스트는 같은 PR에 포함할 수 있다.

---

## Schema Migration과 Data Migration

가능하면 schema 변경과 데이터 변환의 책임을 구분한다.

```text
Schema migration
- 테이블/컬럼/제약/index 구조 변경

Data migration
- 기존 행 변환
- backfill
- 값 재계산
- 데이터 이동
```

대량 데이터 변경이 있으면 다음을 명확히 한다.

```text
- 대상 범위
- 조건
- 예상 영향
- 실패 시 복구 방법
- 반복 실행 가능 여부
```

작은 프로젝트라도 운영 데이터 변경을 schema 변경에 무심코 섞지 않는다.

---

## Destructive Change

아래 변경은 별도 위험 작업으로 취급한다.

```text
- 테이블 삭제
- 컬럼 삭제
- 기존 데이터 삭제
- 컬럼 타입 변경
- 대량 UPDATE
- NOT NULL 강화로 기존 행이 실패할 수 있는 변경
- foreign key / constraint 추가로 기존 데이터가 위반될 수 있는 변경
```

이 경우 구현 전에 최소한 다음을 보고한다.

```text
- 삭제/변환되는 대상
- 기존 데이터 영향
- 백업 또는 복구 방법
- 배포 순서가 필요한지
- 되돌릴 수 없는 부분
```

---

## 승인 규칙

사용자 승인 없이 다음 작업을 하지 않는다.

```text
- migration 파일 생성
- migration 실행
- 기존 데이터 수정/삭제
- 테이블/컬럼 삭제
- 운영 DB 직접 변경
- DB 권한/정책 변경
```

사용자가 특정 DB 변경을 명확히 승인한 경우에도,
그 범위를 넘어서는 추가 schema/data 변경이 필요하면 다시 보고한다.

---

## 운영 DB 원칙

- 운영 DB에 직접 수동 변경하지 않는다.
- 가능한 경우 코드와 migration으로 재현 가능한 변경을 사용한다.
- 운영 데이터가 관련되면 로컬/개발 환경 검증을 먼저 한다.
- 백업이 필요한 변경은 실행 전에 백업 가능 여부를 확인한다.
- 민감한 데이터, 비밀번호, secret, connection string을 출력하지 않는다.

---

## DB 구현 전 출력

필요한 내용만 간결하게 정리한다.

```text
## DB 변경 계획
- 변경 목적:
- 대상 model/table:
- schema 변경:
- 기존 데이터 영향:
- migration 계획:
- 검증 방법:
- 위험/확인 필요:
```

해당 없는 항목은 생략한다.

---

## 검증

DB 변경 후 현재 프로젝트에 맞는 검증을 수행한다.

기본 확인:

```text
- migration 파일이 의도한 변경만 포함하는가?
- migration이 로컬/개발 환경에서 정상 적용되는가?
- 필요한 경우 rollback 또는 복구 경로를 확인했는가?
- 기존 데이터 조회가 깨지지 않는가?
- 새 제약/관계가 의도대로 동작하는가?
- 관련 기능 테스트가 통과하는가?
```

프로젝트에 따라 추가:

```text
- nullable/default 처리
- index/unique 동작
- API 응답
- UI 표시
- 권한 정책
- 대량 데이터 처리 시간
```

실행하지 못한 검증은 이유와 함께 명시한다.

## 작업 완료 보고

```text
## DB 작업 결과
- 변경한 schema/migration:
- 기존 데이터 영향:
- 실행한 검증:
- 실행하지 못한 검증:
- 남은 리스크:
```

필요한 경우에만 적용/rollback 순서를 추가한다.

---

## 토큰 / 문맥 관리

- 현재 변경과 관련 없는 DB 체크리스트는 출력하지 않는다.
- 프로젝트에 없는 개념(API, RLS, 타입 정의 등)을 억지로 검토하지 않는다.
- 이미 코드에서 확인한 사실을 다시 질문하지 않는다.
- 설계 단계에서는 필요한 데이터 규칙까지만 확정하고, 구체적인 ORM/SQL 구현 방식은 구현 단계에서 결정할 수 있다.
- 단순 추가 migration에 과도한 rollback 문서를 만들지 않는다.

---

## 한 줄 원칙

```text
DB 변경은 현재 구조와 데이터를 먼저 확인하고, 필요한 만큼만 설계하고, 승인 후 migration과 검증으로 증명한다.
```
