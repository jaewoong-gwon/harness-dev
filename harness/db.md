# DB / Migration Harness

## 목적

이 문서는 Claude Code가 DB 구조, migration, schema, seed data, query 로직을 다룰 때 지켜야 할 규칙을 정의한다.

목표는 다음과 같다.

1. DB 변경을 즉시 수행하지 않고 먼저 영향 범위를 검토한다.
2. 기존 데이터 손상 가능성을 최소화한다.
3. migration 작성 전 현재 schema와 사용 위치를 확인한다.
4. rollback 가능성을 고려한다.
5. API, UI, 타입 정의와의 연결 영향을 함께 점검한다.

---

## 기본 원칙

1. DB 변경은 일반 코드 변경보다 더 신중하게 다룬다.
2. migration 작성 전 현재 DB 구조와 관련 코드를 먼저 분석한다.
3. 기존 데이터를 삭제하거나 덮어쓰는 변경은 기본적으로 금지한다.
4. 테이블 삭제, 컬럼 삭제, 컬럼 타입 변경은 반드시 사용자 승인 후에만 제안 또는 실행한다.
5. 새 테이블이나 새 컬럼을 추가할 때는 nullable 여부, default 값, index, foreign key를 함께 검토한다.
6. DB 구조 변경이 API, UI, 타입 정의에 미치는 영향을 함께 설명한다.
7. migration 파일 작성과 migration 실행은 별도 승인 단계로 구분한다.
8. 사용자가 “DB 변경 진행” 또는 “migration 작성 진행”이라고 명시하기 전까지 migration 파일을 만들지 않는다.
9. seed data가 필요한 경우 실제 운영 데이터와 구분한다.
10. 민감한 데이터나 환경변수 값을 출력하지 않는다.

## 작업 전 확인 항목

DB 관련 작업 전에는 아래 항목을 확인한다.

```text
- 현재 DB 관련 파일 위치
- schema 또는 migration 파일 존재 여부
- DB client 생성 위치
- API에서 사용하는 테이블과 컬럼
- UI에서 사용하는 데이터 필드
- 타입 정의 파일
- 기존 데이터와의 호환성
- RLS 또는 권한 정책 존재 여부
- seed data 또는 fixture 존재 여부
- local/dev/prod 환경 구분 방식
```

## Migration 작성 전 검토 기준

migration 작성 전 아래 항목을 반드시 확인한다.

```text
- 새 테이블이 필요한가, 기존 테이블 확장으로 충분한가?
- 컬럼명은 기존 네이밍 규칙과 일관되는가?
- nullable 허용 여부가 적절한가?
- default 값이 필요한가?
- unique 제약이 필요한가?
- index가 필요한가?
- foreign key가 필요한가?
- cascade delete가 필요한가?
- created_at, updated_at이 필요한가?
- sort_order, status, is_active 같은 운영 필드가 필요한가?
- 기존 데이터 migration 또는 backfill이 필요한가?
- 기존 API 응답 구조가 깨질 가능성이 있는가?
- 기존 UI에서 null 또는 빈 값을 처리할 수 있는가?
- rollback이 가능한가?
```

## 금지 사항

사용자 승인 없이 아래 작업을 하지 않는다.

```text
- migration 파일 생성
- migration 실행
- 테이블 삭제
- 컬럼 삭제
- 컬럼 타입 변경
- 기존 데이터 삭제
- 기존 데이터 일괄 업데이트
- RLS 정책 변경
- service role key 노출
- 운영 DB 직접 변경
```

## 권장 migration 방식

DB 변경은 가능한 한 아래 순서로 진행한다.

```text
1. 현재 schema 분석
2. 변경 요구사항 정리
3. 관련 코드 사용 위치 확인
4. 새 schema 초안 작성
5. 기존 데이터 영향 범위 검토
6. migration 계획 작성
7. rollback 전략 작성
8. 사용자 승인
9. migration 파일 작성
10. 로컬 또는 개발 환경 검증
11. 타입/API/UI 반영
12. 최종 검증
```

## DB 설계 원칙

새 DB 구조를 제안할 때는 아래 원칙을 우선 검토한다.

```text
- 하나의 테이블은 하나의 명확한 책임을 가진다.
- 중복 저장이 필요한 경우 이유를 설명한다.
- 관계형 데이터는 foreign key 또는 명확한 참조 기준을 둔다.
- 반복되는 하위 데이터는 별도 테이블 분리를 검토한다.
- 정렬이 필요한 데이터는 sort_order 같은 명시적 정렬 필드를 검토한다.
- 공개/비공개 또는 활성/비활성 상태가 필요한 데이터는 status 또는 is_active 필드를 검토한다.
- 생성일과 수정일 추적이 필요한 경우 created_at, updated_at을 검토한다.
- 자주 조회되는 조건에는 index 필요성을 검토한다.
- soft delete가 필요한 경우 deleted_at 또는 status 방식을 검토한다.
- 운영 데이터와 테스트/샘플 데이터를 구분한다.
```

## Migration 초안 출력 형식

사용자가 migration 초안을 요청한 경우에도, 실제 파일 생성 전에는 먼저 아래 형식으로 제안한다.

```text
## Migration 초안

### 목적
- 

### 변경 요약
- 

### SQL 초안
- 실제 SQL은 사용자가 요청하거나 승인한 경우에만 작성한다.

### 적용 전 확인 사항
- 현재 브랜치와 작업 범위를 확인한다.
- 현재 schema와 migration 이력을 확인한다.
- migration 대상 환경이 local/dev/prod 중 어디인지 확인한다.
- 기존 데이터에 영향을 주는지 확인한다.
- API, UI, 타입 정의 변경이 함께 필요한지 확인한다.
- migration 적용 후 실행할 검증 항목을 확인한다.

### rollback 전략
- 단순 추가 변경인지, 데이터 변환이 포함되는지 구분한다.
- 테이블/컬럼 추가는 제거 가능한지 검토한다.
- 데이터 backfill이 있다면 되돌릴 수 있는지 검토한다.
- 타입 변경이나 데이터 삭제가 포함되면 별도 백업 전략을 제안한다.
- rollback SQL이 필요한 경우 사용자 승인 후 별도로 제안한다.

### 검증 방법
- migration을 local 또는 개발 환경에서 먼저 적용한다.
- 기존 주요 query가 정상 동작하는지 확인한다.
- 관련 API 응답이 예상과 일치하는지 확인한다.
- 관련 UI가 null, 빈 값, 기존 데이터를 정상 처리하는지 확인한다.
- 타입 체크 또는 빌드를 실행한다.
- 필요 시 seed data 또는 테스트 데이터를 기준으로 조회 결과를 확인한다.
```

## SQL 초안 작성 기준

SQL 초안은 사용자가 명시적으로 요청하거나 승인한 경우에만 작성한다.

SQL을 작성할 때는 아래 사항을 지킨다.

```text
- destructive change는 기본적으로 작성하지 않는다.
- DROP TABLE, DROP COLUMN, DELETE, TRUNCATE는 별도 경고와 승인 후에만 제안한다.
- 기존 데이터 변환이 필요한 경우 UPDATE 범위와 조건을 명확히 작성한다.
- NOT NULL 컬럼 추가 시 기존 데이터 처리 방식을 함께 제안한다.
- foreign key 추가 시 기존 데이터가 제약 조건을 만족하는지 확인한다.
- index 추가 시 조회 패턴과 필요성을 설명한다.
```

## 데이터 변경 기준

기존 데이터 변경이 필요한 경우, schema 변경과 별도로 다룬다.

```text
- schema migration과 data migration을 가능하면 분리한다.
- 대량 update는 영향 범위와 where 조건을 명확히 한다.
- 운영 데이터에 직접 적용하지 않는다.
- 적용 전 백업 또는 rollback 가능성을 확인한다.
- seed data는 운영 데이터와 혼동되지 않게 구분한다.
```

## RLS / 권한 정책 기준

RLS 또는 권한 정책이 있는 프로젝트에서는 아래 항목을 추가로 확인한다.

```text
- 새 테이블에 RLS가 필요한가?
- 기존 정책과 일관되는가?
- public, authenticated, admin 권한이 구분되는가?
- service role key가 클라이언트에 노출될 가능성은 없는가?
- 읽기, 생성, 수정, 삭제 권한이 각각 필요한가?
```

## 검증 기준

DB 작업 후 아래 항목을 검증한다.

```text
- migration이 정상 적용되는가?
- 기존 데이터 조회가 깨지지 않는가?
- API 응답 구조가 예상과 일치하는가?
- UI가 필요한 필드를 정상 표시하는가?
- nullable 데이터가 있어도 화면이 깨지지 않는가?
- 외래키 관계가 정상 동작하는가?
- 정렬 순서가 정상 반영되는가?
- 권한 정책이 필요한 경우 정상 동작하는가?
- rollback 또는 복구 전략이 있는가?
```
