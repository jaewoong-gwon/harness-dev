# Git / 형상관리 Harness

## 목적

개인 개발 프로젝트에서 Git 작업을 과도하게 복잡하게 만들지 않으면서,
변경 이력과 작업 범위를 명확하게 관리하기 위한 규칙을 정의한다.

목표:

1. 작은 작업은 불필요한 브랜치 없이 빠르게 진행한다.
2. 위험하거나 범위가 큰 작업은 필요할 때만 별도 브랜치로 격리한다.
3. 커밋은 파일 종류가 아니라 의미 있는 변경 목적 단위로 나눈다.
4. commit, push, merge 같은 저장소 변경 작업은 사용자 승인 범위 안에서 수행한다.
5. 구현 결과를 검토하고 되돌릴 수 있는 형태로 남긴다.

---

## 핵심 원칙

```text
작고 명확한 작업은 main에서 직접 진행할 수 있다.
브랜치는 기본 절차가 아니라 위험 관리 수단으로 사용한다.
커밋은 파일 종류가 아니라 변경 목적 기준으로 나눈다.
관련 없는 변경을 하나의 커밋이나 작업에 섞지 않는다.
검증 후 커밋한다.
외부 저장소에 영향을 주는 작업은 승인 없이 수행하지 않는다.
```

---

## 작업 전 확인

Git 작업 전 현재 상태를 먼저 확인한다.

```text
- 현재 브랜치
- 수정된 파일
- 추적되지 않은 파일
- 기존 사용자 변경사항
- 현재 작업과 기존 변경사항의 충돌 가능성
```

필요한 경우에만 추가로 확인한다.

```text
- 최근 커밋 이력
- 기존 브랜치 전략
- 기존 커밋 메시지 관례
- 원격 저장소 상태
```

Git 상태에 문제가 없다면 확인 내용을 매번 길게 보고하지 않는다.

---

## 기본 작업 흐름

### 작은 작업

```text
요구사항 확인
→ 구현 계획
→ 사용자 승인
→ main에서 구현
→ 검증
→ 사용자 리뷰
→ commit 승인
→ git add + commit
→ 필요 시 push
```

### 위험하거나 큰 작업

```text
요구사항 확인
→ 구현 계획
→ 사용자 승인
→ 작업 브랜치 제안
→ 브랜치 승인 및 생성
→ 구현
→ 검증
→ 사용자 리뷰
→ commit 승인
→ git add + commit
→ push 승인
→ 필요 시 Pull Request
→ merge 승인
```

모든 작업에 브랜치나 Pull Request를 강제하지 않는다.

---

## 브랜치 사용 기준

이 harness는 개인 개발 프로젝트를 기본 전제로 하며,
모든 작업에 별도 브랜치를 만들지 않는다.

기본 작업 브랜치는 `main`이다.

범위가 작고 검증 방법이 명확한 작업은
`main`에서 직접 구현하고 커밋할 수 있다.

다음 중 하나에 해당하면 별도 작업 브랜치를 우선 검토한다.

```text
- 변경 범위가 크다.
- 기존 기능을 깨뜨릴 위험이 높다.
- destructive DB/data migration이 포함된다.
- 실험적이거나 폐기 가능성이 있는 구현이다.
- 여러 영역에 걸친 대규모 변경이다.
- 작업 중간 상태를 main에 두기 어렵다.
- 장시간 작업으로 여러 중간 커밋이 예상된다.
- 사용자가 별도 브랜치를 요청했다.
```

브랜치가 필요하지 않은 작업에서는
브랜치 생성을 제안하거나 확인 질문을 반복하지 않는다.

별도 브랜치가 필요하다고 판단한 경우에만
사용자에게 이유와 권장 브랜치 이름을 제시한다.

브랜치를 사용하는 경우 하나의 명확하고 독립적으로 검증 가능한 변경 목적을 가진다.

---

## 브랜치 이름

별도 브랜치를 사용할 경우 기본 형식:

```text
<type>/<short-purpose>
```

기본 type:

```text
feat/
fix/
refactor/
test/
docs/
chore/
```

예:

```text
feat/equipment-kiosk
fix/rental-duplicate-check
refactor/worklog-export
docs/equipment-design
```

브랜치 이름은 짧고 의미 중심으로 작성한다.

내부 작업 번호(PR1, PR2 등)는
프로젝트에서 별도 규칙으로 사용하지 않는 한 브랜치 이름에 강제로 포함하지 않는다.

---

## 작업 단위와 Pull Request

구현 계획의 작업 단위와 GitHub Pull Request는 반드시 1:1일 필요가 없다.

작업 단위는 구현과 검증을 작게 나누기 위한 기준이고,
Pull Request는 변경을 별도로 리뷰하거나 병합할 가치가 있을 때 사용한다.

Pull Request는 다음 상황에서 우선 검토한다.

```text
- 별도 작업 브랜치를 사용했다.
- 변경 범위가 커서 전체 diff 리뷰가 유용하다.
- 위험도가 높은 변경이다.
- 별도 리뷰 단위로 기록할 가치가 있다.
- 사용자가 Pull Request를 요청했다.
```

작고 검증된 변경은 `main`에 직접 커밋할 수 있다.

Pull Request를 사용하는 경우에는 하나의 명확한 변경 목적을 가진다.

---

## 변경 범위 원칙

하나의 작업에는 하나의 명확한 목적을 둔다.

기능 완성에 직접 필요한 변경은 같은 작업에 포함할 수 있다.

예:

```text
장비 대여 모델 추가
→ model
→ migration
→ 관련 test
→ 최소 설정 변경
```

다음 항목은 파일 종류가 다르다는 이유만으로 기계적으로 분리하지 않는다.

```text
- 기능 구현에 필요한 DB schema/migration
- 기능 검증에 필요한 테스트
- 기능 구현에 필요한 최소 UI/API 변경
- 변경 내용을 설명하기 위한 최소 문서 수정
```

반면 목적이 다른 변경은 분리한다.

예:

```text
- 기능과 무관한 리팩토링
- 별도 성능 개선
- 독립적인 UI 개편
- 독립적인 DB 정리
- 코드 스타일 일괄 변경
- 패키지 정리
- 관련 없는 문서 개편
```

변경 파일 수가 많다는 이유만으로 기계적으로 작업을 나누지 않는다.

---

## 커밋 단위

커밋은 파일 종류가 아니라 하나의 의미 있는 변경 목적을 기준으로 나눈다.

하나의 기능을 완성하는 데 직접 필요한
model + migration + test + 최소 설정 변경은 하나의 커밋으로 묶을 수 있다.

다음과 같이 파일 종류만으로 커밋을 기계적으로 나누지 않는다.

```text
model 커밋
migration 커밋
test 커밋
```

반대로 서로 독립적으로 설명할 수 있고
각각 되돌려도 의미가 있는 변경은 별도 커밋으로 나눌 수 있다.

작은 작업을 불필요하게 여러 커밋으로 쪼개지 않는다.

---

## 커밋 메시지 규칙

기본 형식:

```text
type(scope): summary
```

기본 type:

```text
feat      기능 추가 또는 사용자 동작 변경
fix       버그 수정
test      테스트 추가 또는 수정
docs      문서만 변경
refactor  외부 동작 변경 없는 구조 개선
chore     개발환경, 도구, 기타 유지보수
```

`scope`는 변경 영역을 명확하게 표현할 수 있을 때 사용한다.

summary는 기본적으로 한글로 작성한다.

예:

```text
feat(equipment): 장비 대여 및 사용 모델 추가
fix(kiosk): 제출 후 세션 초기화 오류 수정
test(equipment): 모델 기본값 테스트 추가
docs(harness): Git 작업 규칙 보완
refactor(console): 장비 필터 헬퍼 분리
```

emoji는 기본적으로 사용하지 않는다.

프로젝트에서 명시적으로 다른 커밋 메시지 관례를 사용하기로 한 경우에만
해당 프로젝트 규칙을 우선한다.

---

## 승인 규칙

단순 조회 명령은 별도 승인 없이 실행할 수 있다.

예:

```text
git status
git diff
git log
git branch --show-current
git check-ignore
```

구현 승인을 받았더라도 다음 작업은 사용자 승인 전 실행하지 않는다.

```text
git commit
git push
Pull Request 생성
git merge
```

`git add`는 사용자가 커밋을 승인한 경우 해당 커밋 준비 과정에 포함된 것으로 본다.

다음 위험 작업은 항상 별도 승인을 받는다.

```text
force push
git rebase
git reset
git clean
브랜치 삭제
기존 사용자 변경 복원 또는 삭제
충돌 해결 과정에서 기존 변경 삭제
```

현재 작업 트리에 사용자의 기존 변경이 있으면
임의로 덮어쓰거나 정리하지 않는다.

---

## 커밋 전 검증

커밋 전에 최소 다음을 확인한다.

```text
- 승인된 작업 범위를 벗어난 파일이 없는가?
- git diff에 의도하지 않은 변경이 없는가?
- 테스트 또는 해당 작업의 검증이 완료됐는가?
- migration이 있다면 의도한 schema 변경만 포함하는가?
- 민감정보가 포함되지 않았는가?
- .env, venv, 로컬 DB, 임시 파일 같은 로컬 산출물이 포함되지 않았는가?
- git diff --check가 필요한 경우 통과했는가?
```

검증하지 않은 상태에서 완료 또는 안전하다고 단정하지 않는다.

---

## Push / Pull Request / Merge

`git push`는 원격 저장소 상태를 변경하므로 사용자 승인을 받는다.

Pull Request는 사용자가 요청하거나,
별도 브랜치를 리뷰/병합 단위로 사용하는 것이 유용한 경우에만 제안한다.

Pull Request 설명은 필요한 내용만 포함한다.

```text
## 목적
-

## 변경 내용
-

## 검증
-

## 영향 / 리스크
-
```

필요한 경우에만 다음 항목을 추가한다.

```text
- 제외한 작업
- DB/migration 영향
- 관련 문서
- 후속 작업
```

merge는 항상 별도 승인을 받는다.

force push, rebase, reset을 merge 준비 수단으로 임의 사용하지 않는다.

## 구현 전 Git 출력

Git 상태가 실제 작업 계획에 영향을 줄 때만 간결하게 보고한다.

예:

```text
## Git 상태
- 현재 브랜치:
- 기존 변경:
- 충돌 가능성:

## Git 판단
- main 직접 작업 가능 / 별도 브랜치 권장
- 판단 이유:
```

문제가 없다면 Git 상태 전체를 매번 장황하게 출력하지 않는다.

---

## 작업 완료 보고

Git 관련 정보가 필요한 경우 다음 정도로 보고한다.

```text
## Git 작업 보고
- 현재 브랜치:
- 변경 파일:
- 검증:
- 커밋 메시지 제안:
- push/PR 필요 여부:
- 주의사항:
```

PR 본문 전체는 사용자가 요청하거나 실제 PR 생성 직전에만 작성한다.

---

## 토큰 / 문맥 관리

- Git 상태가 작업에 영향이 없으면 긴 Git 보고를 반복하지 않는다.
- 브랜치가 필요하지 않은 작은 작업에서는 브랜치 생성 여부를 반복해서 묻지 않는다.
- 매번 Pull Request 템플릿 전체를 출력하지 않는다.
- 이미 합의된 작업 범위를 반복 설명하지 않는다.
- 기존 코드와 Git 상태에서 확인 가능한 내용을 사용자에게 다시 질문하지 않는다.
- 변경 목적과 직접 관련된 Git 정보만 보고한다.

## 한 줄 원칙

```text
작은 작업은 main에서 검증 후 의미 있게 커밋하고, 위험한 작업만 브랜치로 격리하며, 외부 저장소 변경은 승인 후 수행한다.
```
