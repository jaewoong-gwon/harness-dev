# Git / Version Control Harness

## 목적

이 문서는 Claude Code가 Git 기반 프로젝트에서 작업할 때 지켜야 할 형상관리 규칙을 정의한다.

목표는 다음과 같다.

1. 작업 범위를 PR 단위로 작게 유지한다.
2. 하나의 PR에는 하나의 목적만 담는다.
3. 사용자의 승인 없이 commit, push를 하지 않는다.
4. 변경사항을 추적 가능하게 정리한다.
5. 리뷰 가능한 형태로 작업 결과를 보고한다.

---

## 기본 원칙

1. 하나의 작업은 하나의 명확한 목적을 가져야 한다.
2. 기능 구현, 리팩토링, 문서 수정, DB 변경을 한 PR에 섞지 않는다.
3. PR 단위는 작고 검증 가능해야 한다.
4. 사용자가 승인하기 전까지 git add, git commit, git push를 실행하지 않는다.
5. Claude는 커밋을 직접 수행하기보다 커밋 메시지와 PR 설명 초안을 제안한다.
6. 변경 파일이 많아질 경우 작업을 여러 PR로 나누는 방안을 먼저 제안한다.
7. 기존 브랜치 전략이 있다면 그 전략을 우선 따른다.
8. 현재 브랜치와 변경 상태를 확인한 뒤 작업 계획을 작성한다.

---

## 작업 전 확인

Git 관련 작업 전에는 아래 항목을 확인한다.

```text
- 현재 브랜치
- 변경된 파일 존재 여부
- 추적되지 않은 파일 존재 여부
- 사용자가 작업하려는 대상 PR 또는 이슈
- 현재 작업이 기존 변경사항과 충돌할 가능성
```

---

## 작업 전 출력 형식

```text
## Git 상태 확인

### 현재 브랜치
- 

### 현재 변경사항
- 

### 작업 목적
- 

### 권장 PR 단위
- 

### 이번 PR에 포함할 작업
- 

### 이번 PR에서 제외할 작업
- 

### 사용자 확인 필요 사항
- 
```

---

## PR 단위 분리 기준

다음 작업은 가능하면 별도 PR로 분리한다.

```text
- 프로젝트 초기 설정
- UI 변경
- API 변경
- DB schema 변경
- 인증/권한 변경
- 리팩토링
- 테스트 추가
- 문서 수정
- 스타일 수정
- 패키지 추가
```

---

## 금지 사항

사용자 승인 없이 아래 명령을 실행하지 않는다.

```text
git add
git commit
git push
git merge
git rebase
git reset
git clean
git checkout -- .
git branch -D
```

특히 아래 작업은 반드시 별도 확인을 받는다.

```text
- 기존 변경사항 되돌리기
- 브랜치 삭제
- rebase
- reset
- force push
- conflict 해결
```

---

## 커밋 메시지 제안 형식

Claude는 직접 커밋하지 않고 아래 형식으로 커밋 메시지를 제안한다.

```text
type(scope): summary
```

예시:

```text
feat(product): add section-based product detail rendering
fix(qr): normalize product slug generation
docs(harness): add git workflow rules
refactor(db): split product detail data structure
```

---

## PR 설명 초안 형식

작업 완료 후 PR 설명은 아래 형식으로 제안한다.

```text
## 작업 목적

-

## 변경 내용

-

## 제외한 작업

-

## 검증 방법

-

## 영향 범위

-

## 남은 리스크

-

## 관련 문서 / 이슈

-
```

---

## 검증 기준

PR 제출 전 아래 항목을 확인한다.

```text
- 작업 목적이 하나로 명확한가?
- 변경 파일이 과도하게 많지 않은가?
- 기능 구현과 리팩토링이 섞이지 않았는가?
- DB 변경이 포함되어 있다면 별도 설명이 있는가?
- 테스트 또는 수동 검증 방법이 작성되어 있는가?
- 사용자가 요청하지 않은 변경이 포함되지 않았는가?
```
