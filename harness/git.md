# Git / Version Control Harness

## 목적

Git 기반 프로젝트에서 Claude Code가 작업 범위를 작고 추적 가능하게 유지하도록 하는 형상관리 규칙을 정의한다.

목표:

1. 하나의 PR에는 하나의 명확한 목적만 담는다.
2. 기능과 무관한 리팩토링/정리를 섞지 않는다.
3. 승인 없이 commit, push, merge 같은 변경 작업을 하지 않는다.
4. 현재 Git 상태를 확인한 뒤 작업한다.
5. 구현 결과를 리뷰 가능한 형태로 정리한다.

---

## 핵심 원칙

```text
PR은 목적 기준으로 나눈다.
기능 완성에 필요한 변경은 같은 PR에 포함할 수 있다.
관련 없는 변경은 섞지 않는다.
승인 없이 Git 상태를 변경하지 않는다.
```

---

## 작업 전 확인

Git 작업 전 아래 항목을 확인한다.

```text
- 현재 브랜치
- 수정된 파일
- 추적되지 않은 파일
- 현재 작업과 기존 변경사항의 충돌 가능성
- 기존 브랜치/PR 전략
```

대상 PR이나 이슈가 없는 경우 이를 억지로 요구하지 않는다.

---

## PR 범위 원칙

하나의 PR에는 하나의 사용자 목적 또는 하나의 기능 단위를 담는다.

예:

```text
장비 대여 도메인 추가
→ 모델
→ migration
→ 서비스
→ 해당 기능 테스트
```

처럼 하나의 기능을 완성하기 위해 직접적으로 필요한 변경은 같은 PR에 포함할 수 있다.

따라서 아래 항목은 무조건 별도 PR로 분리하지 않는다.

```text
- 기능 구현에 직접 필요한 DB schema/migration
- 기능 검증에 직접 필요한 테스트
- 기능 구현에 필요한 최소 UI/API 변경
- 변경된 동작을 설명하기 위한 최소 문서 수정
```

반면 목적이 다른 변경은 분리한다.

예:

```text
- 기능 구현과 무관한 리팩토링
- 별도 성능 개선
- 별도 UI 개편
- 독립적인 DB 정리
- 코드 스타일 일괄 변경
- 패키지 정리
- 관련 없는 문서 개편
```

PR을 나누는 기준은 "파일 종류"가 아니라 "변경 목적"이다.

---

## PR 분리 판단

다음 중 하나에 해당하면 별도 PR을 우선 검토한다.

```text
- 사용자 목적이 서로 다름
- 독립적으로 배포/검증 가능함
- 변경 범위가 커져 리뷰가 어려움
- 위험도가 다른 변경이 섞임
- 리팩토링이 기능 구현보다 커짐
- 기존 동작 변경이 별도 검토를 필요로 함
```

변경 파일 수가 많다는 이유만으로 기계적으로 PR을 나누지 않는다.

---

## 승인 규칙

Git 상태를 변경하는 명령은 사용자의 명시적 승인 범위 안에서만 실행한다.

승인 없이 실행하지 않는다.

```text
git add
git commit
git push
git merge
git rebase
git reset
git clean
git checkout -- .
git restore
git branch -D
```

특히 아래 작업은 기존 승인 범위에 포함되어 있더라도 위험도가 높으므로 별도로 확인한다.

```text
- force push
- 기존 변경사항 되돌리기
- 브랜치 삭제
- rebase
- reset
- conflict 해결 과정에서 기존 변경 삭제
```

단순 조회 명령은 실행 가능하다.

예:

```text
git status
git diff
git log
git branch --show-current
```

---

## 브랜치 원칙

1. 기존 프로젝트 브랜치 전략이 있으면 우선 따른다.
2. 새 브랜치가 필요한 경우 이름과 기준 브랜치를 먼저 제안한다.
3. 사용자가 요청하지 않은 브랜치 생성/삭제를 임의로 수행하지 않는다.
4. 현재 작업 트리에 기존 변경이 있으면 덮어쓰거나 정리하지 않는다.
5. 기존 사용자 변경과 이번 작업 변경을 구분한다.

---

## 커밋 원칙

커밋은 하나의 의미 있는 변경 단위로 유지한다.

사용자가 직접 commit을 요청하지 않았다면 커밋 메시지 초안만 제안한다.

기본 형식:

```text
type(scope): summary
```

예:

```text
feat(equipment): add rental domain models
fix(kiosk): reset session after rental request
docs(harness): refine git workflow rules
refactor(console): extract equipment filter helper
```

프로젝트에 기존 커밋 메시지 관례가 있으면 그 관례를 우선한다.

---

## PR 설명

PR 설명에는 필요한 내용만 포함한다.

```text
## 목적
-

## 변경 내용
-

## 검증
-

## 영향 / 리스크
-
```

필요한 경우에만 다음 항목을 추가한다.

```text
- 제외한 작업
- DB/migration 영향
- 관련 이슈/문서
- 후속 작업
```

---

## 구현 전 Git 출력

Git 상태가 실제 작업 계획에 영향을 주는 경우에만 간결하게 보고한다.

```text
## Git 상태
- 브랜치:
- 기존 변경:
- 충돌 가능성:

## 권장 작업 단위
- 이번 PR 목적:
- 포함:
- 제외:
```

문제가 없으면 Git 상태 전체를 매번 장황하게 출력하지 않는다.

---

## PR 제출 전 검증

최소 다음을 확인한다.

```text
- PR 목적이 하나로 설명 가능한가?
- 관련 없는 변경이 포함되지 않았는가?
- 승인된 범위를 넘지 않았는가?
- git diff에 의도하지 않은 파일이 없는가?
- 테스트/검증 결과가 있는가?
- DB 변경이 있다면 migration 영향이 설명되어 있는가?
- 민감정보나 로컬 산출물이 포함되지 않았는가?
```

---

## 작업 완료 보고

Git 관련 정보가 필요한 경우 다음 정도로 보고한다.

```text
## Git 작업 보고
- 변경 파일:
- 검증:
- 커밋 메시지 제안:
- PR 제목 제안:
- 주의사항:
```

PR 본문 전체는 사용자가 요청하거나 실제 PR 생성 직전에 작성한다.

---

## 토큰 / 문맥 관리

- Git 상태가 작업에 영향이 없으면 긴 Git 보고를 반복하지 않는다.
- 매번 PR 템플릿 전체를 출력하지 않는다.
- 이미 합의된 PR 범위를 반복 설명하지 않는다.
- 변경 목적과 직접 관련된 Git 정보만 보고한다.

---

## 한 줄 원칙

```text
파일 종류가 아니라 목적을 기준으로 PR을 나누고, 승인 없이 Git 상태를 변경하지 않는다.
```
