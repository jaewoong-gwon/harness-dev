# UI / UX Harness

## 목적

UI/UX 변경에서 화면 목적, 사용자 흐름, 정보 우선순위, 사용 환경을 먼저 확인하고
기존 디자인 시스템을 해치지 않도록 하는 공통 규칙을 정의한다.

목표:

1. 구현 전에 화면 목적과 사용자를 확인한다.
2. 정보와 행동의 우선순위를 먼저 정한다.
3. 기존 컴포넌트와 스타일을 우선 재사용한다.
4. 주요 상태와 예외 상황을 고려한다.
5. 구현 후 실제 화면 기준으로 검증한다.

---

## 핵심 원칙

```text
예쁘게 만들기 전에 목적을 확인한다.
정보 우선순위와 다음 행동을 명확히 한다.
기존 디자인 시스템을 우선한다.
필요한 화면 상태만 설계한다.
승인 없이 UI 파일을 수정하지 않는다.
```

---

## 적용 범위

다음 작업에 적용한다.

```text
- 신규 화면
- 기존 화면 구조 변경
- 폼/테이블/목록 UI 변경
- CTA/상태 메시지 변경
- 반응형 대응
- CSS/스타일 변경
- 컴포넌트 구조 변경
```

문구 오타 수정처럼 UX 판단이 거의 필요 없는 단순 변경에는 필요한 규칙만 적용한다.

---

## 작업 전 확인

UI 작업 전 현재 작업과 관련된 항목만 확인한다.

```text
- 주요 사용자
- 화면 진입 경로
- 사용자가 해야 할 핵심 행동
- 가장 먼저 보여야 할 정보
- 주요 사용 환경
- 기존 컴포넌트/스타일/디자인 토큰
- 필요한 상태: 정상/빈 상태/오류/로딩/권한 없음 등
```

모든 항목을 기계적으로 출력하지 않는다.

---

## 사용 환경 판단

필요한 경우 우선 환경을 명시한다.

```text
모바일 우선
- 짧은 시간 내 확인/입력이 중요한 화면
- 현장/이동 중 사용하는 화면
- 터치 중심 화면

데스크톱 우선
- 관리자 화면
- 테이블/필터/대량 데이터 관리
- 장시간 업무 화면

둘 다 중요
- 핵심 서비스가 모바일/데스크톱 모두에서 사용됨
```

기존 프로젝트가 특정 환경을 전제로 하고 있다면 그 기준을 우선한다.

---

## 정보 구조

화면은 다음 우선순위를 기준으로 정리한다.

```text
1. 사용자가 가장 먼저 알아야 할 정보
2. 판단에 필요한 핵심 정보
3. 수행해야 할 주요 행동
4. 보조 설명
5. 주의/오류/상태 정보
```

정보가 많으면 의미 단위로 나눈다.
불필요한 장식 때문에 핵심 정보나 행동이 묻히지 않게 한다.

---

## CTA / 상호작용

- 주요 행동은 한눈에 구분되어야 한다.
- 버튼 문구는 실제 행동을 설명해야 한다.
- 위험한 작업은 목적과 결과가 명확해야 한다.
- 같은 중요도의 CTA를 과도하게 늘리지 않는다.
- 아이콘만으로 중요한 행동을 설명하지 않는다.

예:

```text
좋음: 저장하기 / 신청서 제출 / 반납 확정 / 변경 사항 저장
모호함: 확인 / 처리 / 클릭 / 바로가기
```

---

## 폼

폼이 있는 경우 필요한 항목을 확인한다.

```text
- 필수/선택 구분
- 오류 메시지 위치
- 입력값 예시 필요 여부
- 제출/취소 동작
- 입력 중 데이터 유실 가능성
- 긴 폼의 섹션 분리 필요성
```

오류는 가능하면 해당 입력 근처에서 이해할 수 있게 보여준다.

---

## 테이블 / 목록

목록 화면에서는 필요한 경우 다음을 검토한다.

```text
- 중요한 컬럼 순서
- 검색/필터/정렬 필요 여부
- 페이지네이션 필요 여부
- 행 클릭과 개별 버튼 동작 구분
- 빈 목록 상태
- 모바일에서 테이블 유지 여부
```

관리자 화면은 정보 밀도와 반복 작업 효율을 우선한다.

---

## 접근성 / 사용성

현재 화면에 필요한 범위에서 확인한다.

```text
- 텍스트 가독성
- 색상 대비
- 클릭/터치 영역
- 키보드 포커스 필요 여부
- 버튼/링크 구분
- 아이콘 의존 여부
- 이해 가능한 오류 메시지
```

접근성 속성을 기존 이유 없이 제거하지 않는다.

---

## 반응형

반응형이 필요한 경우:

```text
- 핵심 기능이 작은 화면에서도 유지되는가?
- 가로 스크롤이 불필요하게 생기지 않는가?
- 긴 텍스트가 레이아웃을 깨지 않는가?
- 정보 순서가 바뀌어도 의미가 유지되는가?
```

프로젝트가 단일 환경 전용이면 불필요하게 반응형 범위를 확대하지 않는다.

---

## 상태 / 예외 처리

정상 상태 외에 실제로 필요한 상태만 고려한다.

예:

```text
- 데이터 없음
- 로딩
- 저장 실패
- 네트워크 오류
- 권한 없음
- 긴 텍스트
- 일부 데이터 없음
```

존재하지 않는 상황까지 억지로 설계하지 않는다.

---

## 기존 디자인 시스템 우선

1. 기존 컴포넌트, 색상, 간격, 타이포그래피를 우선 재사용한다.
2. 새 디자인 토큰이나 컴포넌트는 기존 구조로 해결하기 어려울 때만 제안한다.
3. 요청 없이 전체 색상/폰트/레이아웃 체계를 바꾸지 않는다.
4. 관련 없는 CSS 정리나 스타일 리팩토링을 섞지 않는다.
5. 기존 화면과 시각적으로 일관되게 유지한다.

---

## 승인 규칙

사용자 승인 없이 다음 작업을 하지 않는다.

```text
- UI 컴포넌트 생성/수정/삭제
- CSS/스타일 수정
- 디자인 시스템 변경
- 색상/폰트 체계 변경
- 대규모 레이아웃 변경
- CTA 문구의 의미 변경
- 요청하지 않은 애니메이션/이미지/장식 추가
```

승인된 화면 목적을 넘어서는 UI 변경이 필요하면 먼저 보고한다.

---

## 구현 전 출력

필요한 경우 아래 정도로 간결하게 정리한다.

```text
## UI 변경 계획
- 화면 목적:
- 주요 사용자/환경:
- 핵심 정보와 행동:
- 재사용할 기존 구조:
- 변경 예정 파일:
- 상태/예외 처리:
- 검증 방법:
```

해당 없는 항목은 생략한다.

와이어프레임이 필요한 작업이면 텍스트 수준의 구조만 먼저 제안한다.

---

## 검증

UI 구현 후 실제 화면 기준으로 확인한다.

```text
- 핵심 정보와 CTA가 명확한가?
- 기존 디자인과 일관되는가?
- 주요 사용 환경에서 레이아웃이 깨지지 않는가?
- 폼/버튼/링크가 정상 동작하는가?
- 필요한 빈 상태/오류 상태가 동작하는가?
- 긴 텍스트나 일부 누락 데이터로 화면이 깨지지 않는가?
- 접근성상 명백한 문제가 없는가?
```

가능하면 실제 브라우저/기기 또는 프로젝트에서 사용하는 검증 방식으로 확인한다.
실행하지 못한 검증은 이유를 명시한다.

---

## 작업 완료 보고

```text
## UI 작업 결과
- 변경 화면/파일:
- 주요 변경:
- 검증:
- 미검증:
- 남은 리스크:
```

필요한 경우에만 반응형/접근성/CTA 세부사항을 추가한다.

---

## 토큰 / 문맥 관리

- 단순 UI 수정에 전체 UX 체크리스트를 출력하지 않는다.
- 현재 화면과 무관한 모바일/데스크톱 규칙을 반복하지 않는다.
- 이미 존재하는 디자인 시스템 설명을 매번 재작성하지 않는다.
- 설계와 구현 계획을 필요 이상으로 분리하지 않는다.
- 사용자에게 코드에서 확인 가능한 UI 구조를 다시 질문하지 않는다.
- 작업에 필요한 수준까지만 와이어프레임/상태를 설계한다.

---

## 한 줄 원칙

```text
사용 목적과 정보 우선순위를 먼저 정하고, 기존 디자인을 최대한 재사용해 필요한 만큼만 바꾼다.
```
