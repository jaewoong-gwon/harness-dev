# UI / UX Harness

## 목적

이 문서는 Claude Code가 UI 또는 UX와 관련된 작업을 수행할 때 지켜야 할 공통 규칙을 정의한다.

목표는 다음과 같다.

1. 바로 화면을 구현하지 않고 먼저 사용자, 목적, 정보 구조를 검토한다.
2. 모바일 또는 데스크톱 중 어떤 환경을 우선해야 하는지 먼저 판단한다.
3. 사용 목적, 정보 우선순위, 가독성, 접근성, 상태 처리를 기준으로 UI를 설계한다.
4. 구현 전 설계안과 구현 계획을 먼저 작성한다.
5. 구현 후 실제 화면 기준의 검증 결과를 보고한다.

---

## 기본 원칙

1. UI 작업은 구현 전에 화면 목적과 사용자 시나리오를 먼저 정의한다.
2. 사용자가 어떤 상황에서 해당 화면을 보는지 먼저 정리한다.
3. 화면에서 가장 중요한 정보와 행동을 우선순위로 정한다.
4. 모든 정보를 같은 크기, 같은 굵기, 같은 배치로 표현하지 않는다.
5. 제목, 본문, 보조 문구, 상태 메시지, 경고, CTA의 역할을 구분한다.
6. 정보가 많을 경우 의미 단위로 나누어 표현한다.
7. 사용자가 다음에 해야 할 행동은 명확하게 안내한다.
8. 기존 디자인 시스템, 컴포넌트 구조, 스타일 규칙이 있다면 우선 따른다.
9. 사용자의 승인 전에는 UI 관련 파일을 생성, 수정, 삭제하지 않는다.
10. 구현 후에는 실제 화면 기준으로 검증 결과를 보고한다.

## 작업 전 확인 항목

UI/UX 작업 전에는 아래 항목을 확인한다.

```text
- 이 화면의 주요 사용자는 누구인가?
- 사용자는 어떤 경로로 이 화면에 들어오는가?
- 사용자는 이 화면에서 무엇을 가장 먼저 알아야 하는가?
- 사용자는 이 화면에서 어떤 행동을 해야 하는가?
- 이 화면의 주요 사용 환경은 모바일인가, 데스크톱인가, 둘 다인가?
- 기존 컴포넌트 구조가 있는가?
- 기존 스타일 방식이 있는가?
- 기존 디자인 토큰, 컬러, 폰트 규칙이 있는가?
- 접근성 또는 반응형 처리가 필요한가?
- 데이터가 없거나 길어질 때 화면이 깨질 가능성이 있는가?
- 로딩, 에러, 권한 없음, 빈 상태가 필요한가?
```

## 모바일 / 데스크톱 우선순위 판단 기준

UI 작업을 시작하기 전에 모바일 우선인지, 데스크톱 우선인지 먼저 판단한다.

### 모바일 우선이 적합한 경우

```text
- 사용자가 외부 이동 중 접근할 가능성이 높은 화면
- QR, 링크, 알림, 문자, 메신저 등을 통해 진입하는 화면
- 짧은 시간 안에 핵심 정보 확인이 필요한 화면
- 입력 항목이 적고 빠른 행동이 중요한 화면
- 일반 고객 또는 불특정 사용자가 접근하는 화면
- 모바일 트래픽 비중이 높거나 높을 것으로 예상되는 화면
```

### 데스크톱 우선이 적합한 경우

```text
- 관리자 화면
- 대시보드
- 데이터 테이블 중심 화면
- 여러 항목을 비교하거나 관리하는 화면
- 복잡한 폼 입력이 필요한 화면
- 장시간 작업하는 업무용 화면
- 파일 업로드, 일괄 처리, 설정 관리가 필요한 화면
```

### 둘 다 중요하게 설계해야 하는 경우

```text
- 고객용 화면과 관리자용 화면이 함께 있는 서비스
- 모바일에서 조회하고 데스크톱에서 관리하는 서비스
- 반응형 웹으로 제공되는 핵심 서비스 화면
- 사용 환경을 특정하기 어려운 공통 화면
```

### 판단 결과 출력 기준

구현 전 아래 형식으로 우선순위를 명시한다.

```text
## 사용 환경 판단

### 우선 설계 환경
- 모바일 우선 / 데스크톱 우선 / 반응형 동시 고려

### 판단 이유
- 

### 보조로 고려할 환경
- 

### 주의할 점
- 
```

## 정보 구조 설계 기준

화면 정보는 아래 순서로 정리한다.

```text
1. 사용자가 가장 먼저 알아야 하는 정보
2. 사용자가 판단에 필요한 핵심 정보
3. 보조 설명
4. 주의사항 또는 확인사항
5. 다음 행동을 유도하는 CTA
```

정보가 많을 경우 하나의 긴 영역에 모두 넣지 않고, 의미 단위로 나눈다.

```text
- 화면 제목
- 한 줄 요약
- 핵심 정보
- 상세 정보
- 입력 영역
- 상태 정보
- 주의사항
- 보조 설명
- CTA
```

## 타이포그래피 계층 기준

텍스트는 역할에 따라 구분한다.

```text
Display
- 화면에서 가장 중요한 제목 또는 대표 문구
- 한 화면에 과도하게 많이 사용하지 않는다.

Heading
- 주요 섹션 제목
- 화면 구조를 빠르게 파악할 수 있게 한다.

Title
- 작은 정보 묶음의 제목
- 카드, 리스트, 폼 그룹 등 내부 제목에 사용한다.

Label
- 버튼, 태그, 상태값, 입력 필드명, 짧은 보조 정보에 사용한다.

Paragraph
- 일반 본문 설명에 사용한다.
- 긴 문단은 적절히 분리한다.

Callout
- 경고, 주의사항, 중요한 안내에 사용한다.
- 일반 본문과 시각적으로 구분한다.

Caption
- 부가 설명, 작은 안내 문구, 보조 정보에 사용한다.
```

## 긴 텍스트 처리 기준

긴 텍스트는 그대로 한 덩어리로 출력하지 않는다.

```text
- 한 영역 안의 본문은 가능한 한 짧게 유지한다.
- 의미가 다른 문장은 별도 섹션으로 나눈다.
- 절차나 조건은 리스트로 표현한다.
- 중요한 안내는 callout으로 분리한다.
- 반복 정보는 카드, 테이블, 리스트 중 적절한 형태를 선택한다.
- 원문 콘텐츠를 임의로 삭제하거나 새로 창작하지 않는다.
- 필요한 경우 원문은 유지한 상태에서 표시 방식만 분리한다.
```

## 레이아웃 설계 기준

레이아웃은 구현 전 먼저 와이어프레임 수준으로 제안한다.

일반적인 화면 구조는 아래 단위로 검토한다.

```text
- 상단 영역
- 핵심 정보 영역
- 주요 행동 영역
- 상세 정보 영역
- 보조 정보 영역
- 상태 / 오류 / 안내 영역
- CTA 영역
```

모바일 화면에서는 아래 기준을 우선한다.

```text
- 중요한 정보가 초반에 보이는가?
- CTA가 명확하게 보이는가?
- 터치하기 쉬운 크기와 간격인가?
- 텍스트가 너무 빽빽하지 않은가?
- 긴 스크롤에서도 섹션 구분이 명확한가?
- 가로 스크롤이 생기지 않는가?
```

데스크톱 화면에서는 아래 기준을 우선한다.

```text
- 넓은 화면을 의미 있게 활용하는가?
- 정보 밀도가 과하거나 부족하지 않은가?
- 테이블, 필터, 검색, 정렬 구조가 명확한가?
- 주요 작업 버튼의 위치가 자연스러운가?
- 반복 작업을 줄일 수 있는 구조인가?
- 사이드바, 헤더, 본문 영역의 역할이 명확한가?
```

## CTA 기준

CTA 버튼은 사용자의 다음 행동을 명확하게 안내해야 한다.

```text
- 버튼 문구는 짧고 명확해야 한다.
- 버튼의 목적이 모호하면 안 된다.
- 주요 CTA와 보조 CTA의 시각적 위계를 구분한다.
- 같은 중요도의 CTA를 과도하게 많이 배치하지 않는다.
- 외부 링크 또는 위험한 작업은 사용자가 이해할 수 있게 표시한다.
```

비추천 예시:

```text
확인하기
더보기
바로가기
클릭
처리
```

추천 예시:

```text
저장하기
초대 보내기
상세 정보 보기
결제 진행하기
신청서 제출하기
관리자 화면으로 이동
변경 사항 저장
삭제 요청하기
```

## 폼 UI 기준

입력 화면이 포함된 경우 아래 항목을 검토한다.

```text
- 필수 입력값과 선택 입력값이 구분되는가?
- 입력 예시 또는 placeholder가 필요한가?
- 오류 메시지가 입력값 근처에 표시되는가?
- 제출 전 확인이 필요한 작업인가?
- 저장, 취소, 초기화 버튼의 역할이 명확한가?
- 입력 중 데이터 유실 가능성이 있는가?
- 긴 폼은 섹션 단위로 나누는 것이 적절한가?
```

---

## 테이블 / 목록 UI 기준

데이터 목록 화면이 포함된 경우 아래 항목을 검토한다.

```text
- 사용자가 가장 많이 확인하는 컬럼이 앞에 있는가?
- 검색, 필터, 정렬이 필요한가?
- 페이지네이션 또는 무한 스크롤이 필요한가?
- 행 클릭과 버튼 클릭의 동작이 혼동되지 않는가?
- 빈 목록 상태가 필요한가?
- 모바일에서 테이블을 그대로 보여줄지 카드형으로 바꿀지 검토했는가?
```

## 접근성 / 사용성 기준

UI 구현 전후로 아래 항목을 확인한다.

```text
- 텍스트 크기가 너무 작지 않은가?
- 색상 대비가 낮지 않은가?
- 버튼과 링크를 구분할 수 있는가?
- 클릭 또는 터치 가능한 영역이 충분한가?
- 아이콘만으로 의미를 전달하지 않는가?
- 이미지가 없어도 핵심 정보를 이해할 수 있는가?
- 키보드 접근 또는 포커스 흐름이 필요한 화면인가?
- 에러 메시지가 사용자가 이해할 수 있는 문장인가?
```

---

## 반응형 기준

반응형 UI가 필요한 경우 아래 항목을 확인한다.

```text
- 우선 설계 환경을 먼저 정했는가?
- 보조 환경에서도 핵심 기능을 사용할 수 있는가?
- 카드, 버튼, 텍스트가 화면 폭에 따라 자연스럽게 줄바꿈되는가?
- 가로 스크롤이 생기지 않는가?
- 긴 텍스트와 긴 URL이 레이아웃을 깨지 않는가?
- 모바일과 데스크톱에서 정보 순서가 달라져도 의미가 유지되는가?
```

---

## 데이터 예외 처리 기준

UI는 정상 데이터만 기준으로 설계하지 않는다.

아래 상태를 함께 고려한다.

```text
- 데이터 없음
- 일부 데이터 없음
- 긴 제목
- 긴 본문
- 긴 URL
- 이미지 없음
- 잘못된 링크
- 로딩 중
- 에러 발생
- 권한 없음
- 저장 실패
- 네트워크 실패
```

데이터가 없는 경우에도 화면이 깨지지 않아야 하며, 사용자에게 현재 상태와 다음 행동을 명확히 안내해야 한다.

---

## 금지 사항

사용자 승인 없이 아래 작업을 하지 않는다.

```text
- UI 컴포넌트 파일 수정
- CSS 또는 스타일 파일 수정
- 디자인 시스템 변경
- 색상 체계 변경
- 폰트 변경
- 레이아웃 구조 대규모 변경
- 기존 컴포넌트 삭제
- 접근성 속성 제거
- CTA 문구 임의 변경
- 사용자가 요청하지 않은 애니메이션 추가
- 사용자가 요청하지 않은 이미지 또는 장식 요소 추가
```

## 검증 기준

UI 작업 후 아래 항목을 검증한다.

```text
- 화면 목적에 맞게 핵심 정보가 먼저 보이는가?
- 정보 우선순위가 시각적으로 구분되는가?
- CTA가 명확하게 보이는가?
- 우선 설계 환경에서 레이아웃이 깨지지 않는가?
- 보조 환경에서도 핵심 기능을 사용할 수 있는가?
- 긴 텍스트가 화면을 과도하게 밀어내지 않는가?
- 데이터가 없을 때도 화면이 깨지지 않는가?
- 버튼과 링크가 정상 동작하는가?
- 로딩, 에러, 빈 상태가 고려되었는가?
- 접근성상 문제가 될 만한 색상, 크기, 클릭 영역이 없는가?
```
